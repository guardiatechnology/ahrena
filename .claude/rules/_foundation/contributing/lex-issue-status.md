# Lexis: Canonical Status Labels on Issue and PR

> **Prefix:** `lex-` | **Type:** Unbreakable Law | **Scope:** Issues and Pull Requests in Guardia repositories that participate in the Issue-Driven flow

## Law

> **Every Issue and every PR participating in the Issue-Driven flow MUST carry exactly one `status: <name>` label from the canonical set (`status: todo`, `status: development`, `status: to review`, `status: review`, `status: to release`, `status: release`, `status: done`), mirroring the `status:` of the corresponding plan. No agent MUST apply two `status: *` labels simultaneously to the same Issue or PR. The `status:*` label is orthogonal to Discovery labels (`pending-spec`/`spec-ready`) and to type labels (`feature request ➕`, `user story 🎯`, etc.) — multiple axes coexist on the same Issue.**

## Coverage

- **Applies to:** all Issues opened via approved templates (`feature-request`, `user-story-for-api`, `user-story-for-frontend`, `simple-task`, `subtask`) and all PRs in Guardia repositories.
- **Bound agents:** `warrior-eunomia` (applies `status: todo` on creation), `warrior-athena` (moves `todo → development`, `development → to review`, `to review → to release`), `warrior-argos` (moves `to review ↔ review`), `warrior-janus` (moves `to release → release → done`), and any agent that creates or modifies Issues/PRs.
- **Exceptions:**
  - **Epic** does not receive `status:*` — it is decomposed into child Issues, each with its own cycle. The Epic closes when all children (`Tracked by`) reach `done`.
  - **Issues generated by Dependabot** or security scanners follow their own flow and are exempt.

## Rules

### 1. Canonical set of 7 labels

| Label | Suggested color | When to apply | Owner |
|---|---|---|---|
| `status: todo` | `#cccccc` (light gray) | Plan created, Issue opened, branch linked, worktree ready | `warrior-eunomia` (fallback: session agent) |
| `status: development` | `#83d2ff` (light blue) | Implementation in progress (Athena Phase 4) | `warrior-athena` |
| `status: to review` | `#fff3a3` (light yellow) | PR opened, waiting for reviewer to pick up | `warrior-athena` (entry); `warrior-argos` (return from `review`) |
| `status: review` | `#fbca04` (yellow) | Argos or human actively reviewing | `warrior-argos` |
| `status: to release` | `#ffb178` (light orange) | Review approved, waiting for release to start | `warrior-athena` |
| `status: release` | `#e07400` (orange) | Release in execution (tag/build/deploy) | `warrior-janus` |
| `status: done` | `#0e8a16` (green) | Release completed, PR merged, cycle closed | `warrior-janus` |

The label description on GitHub MUST contain the condensed semantics of the state for fast visual audit.

### 2. Mutex between `status:*` labels

At any instant, the Issue or PR MUST carry **exactly one** `status:*` label. Each transition executes via:

```bash
gh issue edit {N} --remove-label "status: <previous>" --add-label "status: <next>"
gh pr edit {N}    --remove-label "status: <previous>" --add-label "status: <next>"
```

Applying two `status:*` labels simultaneously (e.g.: `status: to review` + `status: review`) is FORBIDDEN.

### 3. Sync with the plan

The `status:*` label on the Issue MUST mirror the `status:` of the corresponding plan front-matter at every instant. The agent executing the transition (per `lex-agent-planning` "Owners of Each Transition") MUST simultaneously update:

1. `status:` in the plan front-matter.
2. `status: <name>` label on the Issue.
3. `status: <name>` label on the PR (starting at `to review`).

Failure on any of the three produces drift detectable at Gate 2 (per `kata-quality-gate`).

### 4. Orthogonality with Discovery labels

Discovery labels (`pending-spec`, `spec-ready`, defined by plan-038) operate on a separate axis:

- `pending-spec`/`spec-ready` control **entry** into the Athena flow for US-child (User Story child of Epic). They coexist with `status:*` on the same Issue.
- US-child created by Calliope is born with `pending-spec` and **without** `status:*`. It receives `status: todo` only when it gains `spec-ready` (transition done by the corresponding PM after producing the spec).
- Bug and Tech-task skip the spec gate and receive `status: todo` directly on creation by Eunomia.

### 5. Epic does not receive `status:*`

Epic is decomposed by Calliope (plan-038) and never goes through Athena directly. The Epic has no `todo → development → ...` cycle of its own; its state is derived from `Tracked by` (children with `status:*`). Applying `status:*` to an Epic is FORBIDDEN.

### 6. Initial label creation in the repository

Each repository adopting the flow MUST create the 7 labels via `gh label create` (idempotent script at `scripts/bootstrap_status_labels.sh` or dedicated kata). Manual creation via GitHub UI is also acceptable, provided it respects canonical names, colors, and descriptions.

## HARD-GATE

Per [`lex-hard-gate-pattern`](../quality/lex-hard-gate-pattern.md), the textual block of this Lex is canonically expressed as:

```
<HARD-GATE>
warrior-eunomia, warrior-athena, warrior-argos, warrior-janus and any
other agent MUST NOT apply a `status:*` label on an Issue or PR
without satisfying ALL criteria:

  (a) Label belongs to the canonical set of 7
      (status: todo | development | to review | review | to release
       | release | done)
  (b) Issue/PR is not in a terminal state (done|abandoned) when
      receiving the new label
  (c) No other `status:*` label remains on the Issue/PR after the
      transition (mutex applied)
  (d) Corresponding plan had `status:` updated in the same step
  (e) Issue is not an Epic (Epic does not receive status:*)

This rule applies to EVERY Issue and EVERY PR in the Issue-Driven
flow, regardless of:
  - perceived size ("it's just a chore")
  - urgency ("production fire")
  - who asked ("the CEO requested")
  - team confidence ("we already tested")

Declared exception: Epic and Issues generated by Dependabot/scanners
follow their own flow. Every other type of Issue/PR in the
Issue-Driven flow respects the mutex.
</HARD-GATE>
```

## Examples

### Correct

```bash
# Eunomia creates Issue #90 and plan-043 in "todo"
gh issue edit 90 --add-label "status: todo"
# (plan-043 front-matter: status: todo)

# Athena enters Phase 4
gh issue edit 90 --remove-label "status: todo" --add-label "status: development"
# (plan-043 front-matter: status: development)

# Athena opens PR #91 — applies label simultaneously
gh pr create ... && gh pr edit 91 --add-label "status: to review"
gh issue edit 90 --remove-label "status: development" --add-label "status: to review"
# (plan-043 front-matter: status: to review)

# Argos starts review
gh pr edit 91 --remove-label "status: to review" --add-label "status: review"
gh issue edit 90 --remove-label "status: to review" --add-label "status: review"
# (plan-043 front-matter: status: review)
```

### Incorrect

```bash
# ❌ Two simultaneous status:* labels
gh issue edit 90 --add-label "status: to review" --add-label "status: review"

# ❌ Label applied without updating the plan (drift)
gh issue edit 90 --add-label "status: development"
# (plan-043 stayed at status: todo)

# ❌ Applying status:* to Epic
gh issue edit 100 --add-label "status: development"
# Issue #100 has Issue Type Epic
```

## Automated Validation

- **Tool:**
  - Script `scripts/bootstrap_status_labels.sh` creates the 7 labels idempotently in any repository.
  - PR review (human or Argos) verifies alignment among plan `status:`, Issue label, and PR label.
  - Periodic verification GitHub Action (future) detects:
    - Issues/PRs with 0 or ≥2 `status:*` labels
    - Issues with Issue Type Epic carrying `status:*`
    - Drift between plan `status:` and Issue label
- **Timing:** on Issue open/update, on PR open/update, on every owner transition, at Gate 2 (`kata-quality-gate`).
- **Metric:** 0 Issues/PRs with `status:*` label divergent from the corresponding plan; 0 Epics with `status:*`; 100% of transitions executed by the declared owner.
